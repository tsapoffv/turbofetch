# TurboFetch — техстек и архитектура

Документ для разработчика, который хочет разобраться в проекте и продолжить его
копать. Здесь не «что умеет приложение», а как оно устроено внутри: какие
решения приняты, почему именно так, где лежат грабли.

Описание продукта для ресерча — `docs/TurboFetch.pdf`, исходное ТЗ —
`docs/ORIGINAL-BRIEF.md`.

---

## 1. Что это за приложение

TurboFetch скачивает **напрямую с CDN** площадок: YouTube, TikTok, X, Instagram,
SoundCloud, Spotify.
Принципиальное отличие от обычных приложений — нет собственного сервера,
который режет скорость и вставляет рекламу. Байты файла идут от CDN к телефону.

Отсюда же растут две особенности, которые определяют всю архитектуру:

- площадки отдают **подписанные ссылки** — они протухают за минуты. Значит,
  ссылку надо переразбирать перед каждой попыткой;
- видео и звук часто лежат **разными дорожками** (DASH у YouTube). Значит,
  нужен контейнер, в который их можно собрать без перекодирования.

Приложение не публикуется в магазинах, ставится установкой APK.

### 2.3. Нативная часть

ffmpeg собирается вручную под `arm64-v8a` (скрипт `tools/build-ffmpeg.sh`,
ffmpeg-android-maker, NDK r27c, `--enable-libmp3lame`). Готовые `.so` в git
не лежат — 22 МБ бинарей, их проще воспроизвести, чем тащить в репозиторий.

Две детали, без которых ffmpeg не запустится на Android:

- CLI-бинарник переименован в `libffmpegcli.so`. PackageManager распаковывает
  в `nativeLibraryDir` только файлы с именем `lib*.so`, а запускать исполняемый
  файл разрешено **только** из `nativeLibraryDir` — из домашней папки
  приложения запуск запрещён политикой W^X (write-once, execute-never);
- в `build.gradle.kts` включено `jniLibs.useLegacyPackaging = true`. По
  умолчанию AGP грузит нативные библиотеки прямо из APK, не распаковывая на
  диск, — из такого места их запустить нельзя.

Бинарники собраны с выравниванием страниц памяти 16 КБ (требование Android 15).

## 3. Слои и правило зависимостей

```
ui/          Compose-экраны и ViewModel'ы
  │          знает только про domain
  ▼
domain/      модель задачи, форматы, правила, интерфейс DownloadEngine
  ▲
data/        Room, MediaStore, резолверы площадок, HTTP
worker/      фоновая загрузка через WorkManager
```

Правило одно и жёсткое: **domain не знает ни про Android, ни про OkHttp, ни про
Room**. В нём живут `DownloadTask`, `MediaFormat`, `MediaInfo`, `AppSettings`,
`FileNameTemplate`, `QualityPreset` и интерфейс `DownloadEngine`.

Три шва, через которые слои общаются:

- `DownloadEngine` (`domain/engine`) — единственная точка, где UI знает о
  загрузке. Две реализации: `RealDownloadEngine` (боевая) и `FakeEngine`
  (имитация для ранних этапов и тестов);
- `VideoResolver` (`domain/resolver`) — интерфейс площадки: «дай мне форматы
  по ссылке». Реализации лежат в `data/resolver`;
- `Source` (`domain/model`) — enum площадок, по нему выбирается резолвер.

DI — ручной, без Hilt: `core/di/AppContainer`. Проект маленький, фреймворк
был бы лишним; контейнер — обычный класс с `by lazy`-свойствами, он же
единственное место, где выбирается конкретная реализация движка.

## 4. Путь данных: от ссылки до файла

Полный маршрут, шаг за шагом. Это самая полезная карта проекта.

**Шаг 1. Ссылка попадает в приложение.**
Три входа: поле ввода на экране очереди, «Поделиться» из другого приложения
(intent-filter `ACTION_SEND` с `text/plain`) и клик по ссылке в браузере
(intent-filter `ACTION_VIEW` для http/https). Обработка — `MainActivity`.

**Шаг 2. Разбор ссылки — `domain/link/LinkParser`.**
Берёт первый URL из присланного текста (регулярка `https?://\S+`), срезает
хвостовую пунктуацию, определяет площадку через `Source.fromHost(host)` и
извлекает идентификатор ролика. Идентификаторы разные у площадок:

- YouTube: `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `?v=<id>`, иначе
  последний сегмент пути;
- TikTok: последний непустой сегмент пути;
- X: сегмент после `/status/`;
- Instagram: последний значимый сегмент пути — shortcode (`/p/`, `/reel/`,
  `/reels/`, `/tv/`, `/share/p/`);
- SoundCloud: последний сегмент пути — slug трека;
- Spotify: последний значимый сегмент пути — идентификатор трека.

**Шаг 3. Задача попадает в базу — `QueueViewModel.addLink`.**
Создаётся `DownloadTask` со статусом `PENDING`, пишется в Room через
`TaskRepository`. Пользовательские настройки (пресет качества, «только
аудио») применяются сразу.

**Шаг 4. Probe — разбор ссылки площадкой.**
`QueueViewModel.probe` вызывает `engine.probe(url)`. `RealDownloadEngine`
определяет площадку, находит резолвер и просит у него форматы. Резолвер
возвращает `MediaInfo` — список `MediaFormat` (id, подпись, высота, битрейт,
mime, наличие видео/звука, размер, **прямая ссылка** и **заголовки**, которые
требует CDN).

Задача переходит в `PROBING`, потом в `READY`. Если пользователь просил «только
аудио», выбирается аудиодорожка; если её нет — звук потом вытащится из видео
через ffmpeg.

**Шаг 5. Запуск — `QueueViewModel.download` → `DownloadScheduler.enqueue`.**
Создаётся `OneTimeWorkRequest` для `DownloadWorker`:

- ограничения: `NetworkType.CONNECTED`, либо `UNMETERED`, если включено
  «качать только по Wi-Fi»;
- `BackoffPolicy.EXPONENTIAL` от 30 секунд;
- уникальное имя работы `download-<taskId>`, политика `REPLACE`.

**Шаг 6. Worker — `worker/DownloadWorker`.**
Это самая крупная и самая интересная часть (19 КБ). Разбираю её подробно.

Перед основной работой worker:

- ставит себя foreground-сервисом (`FOREGROUND_SERVICE_TYPE_DATA_SYNC` на
  API 29+, канал «Загрузки», notification id 4711);
- решает, нужен ли повторный probe: `needsProbe = selectedFormat?.url.isNullOrBlank() || needsRefresh`.
  Если да — статус `PROBING`, повторный `engine.probe`, формат выбирается
  заново (сначала по id, потом по label, потом прежний, потом первый);
- берёт слот в общем `Semaphore(MAX_PARALLEL_DOWNLOADS = 3)` — это и есть лимит
  параллельных загрузок. Слот освобождается в `finally` под
  `withContext(NonCancellable)`, иначе при отмене лимит «залипал» бы.

Сначала worker решает, **что именно качать**:

- если пользователь просил только аудио — берётся аудиодорожка: либо сам
  выбранный формат, либо парный `audioFormat`;
- если видео идёт **без звука** (DASH у YouTube) — нужна отдельная
  аудиодорожка, она и будет скачана вторым файлом;
- иначе — один файл со звуком.

Дальше:

1. **Имя файла** — `FileNameTemplate.render()` с шаблоном из настроек
   (`{title}_{quality}.{ext}` по умолчанию). Поддерживаемые плейсхолдеры:
   `{title}`, `{author}`, `{quality}`, `{ext}`, `{date}`, `{id}`. `sanitize`
   вырезает символы, запрещённые в именах файлов (`\ / : * ? " < >`) и
   управляющие символы, обрезает до 120 символов.
2. **Рабочий каталог** — `cacheDir/downloads`, имена файлов по id задачи:
   `<id>.video`, `<id>.audio`, `<id>.merged.mp4`.
3. **Статус** → `RUNNING`, прогресс пишется в базу по мере скачивания.
4. **Скачивание** — `engine.download(DownloadRequest)` возвращает
   `Flow<DownloadProgress>`; worker подписывается и пишет прогресс в Room.
5. **Разбор ошибки.** Ошибка бывает двух видов:
   - `retryable = true` (обрыв сети, таймаут, HTTP 5xx/408/429) → задача
     помечается `needsRefresh = true` и worker возвращает `Result.retry()`.
     Частично скачанные файлы **не удаляются** — докачка продолжит их с
     места обрыва;
   - `retryable = false` (HTTP 4xx, кроме 408/429) → `FAILED` и
     `Result.failure()`, повторов не будет.

   Флаг `needsRefresh` — ключевой: подписанная ссылка протухла, перед
   повтором её надо переразобрать заново.
6. **Склейка** — если скачаны видео и аудио отдельно, `MediaMuxerMerger.merge()`
   собирает один MP4.
7. **mp3** — если нужен только звук в mp3, `FfmpegRunner.convertToMp3()`
   перекодирует.
8. **Запись в хранилище** — `MediaStoreWriter.save()`.
9. **Финал** — статус `COMPLETED`, `outputUri` в задаче, уведомление, при
   желании автооткрытие файла плеером. Важная деталь: после успешной записи
   задача **удаляется из таблицы `tasks`** — очередь живёт только для того, что
   «ещё предстоит скачать», а результат уезжает в таблицу `files`. Из-за
   этого статус `COMPLETED` в UI очереди практически недостижим (см. 13.2).
   Временные файлы удаляются, а в историю пишется `DownloadedFile`. Если
   `openAfterDownload` включён и приложение на переднем плане — файл
   открывается через `ACTION_VIEW`, иначе приходит уведомление «Файл готов» с
   `PendingIntent` (id 4712).

**Шаг 7. Файл в галерее — `data/storage/MediaStoreWriter`.**
На Android 10+ (API 29) запись идёт через MediaStore, разрешения на хранилище
не нужны: видео → `Movies/TurboFetch`, аудио → `Music/TurboFetch`, флаг
`IS_PENDING` снимается после копирования. На Android 8–9 — прямой доступ к
публичной папке. Возвращается `content://`-URI.

**Шаг 8. История.**
`FileRepository` отдельно хранит скачанные файлы (`files` в Room), чтобы
очередь и история не мешали друг другу.

## 5. Устойчивость к обрывам связи

Отдельный кусок логики, который стоит знать: `RealDownloadEngine.download`.

- Перед запросом проверяется, есть ли уже частично скачанный файл. Если да —
  добавляется заголовок `Range: bytes=<скачано>-`.
- Ответ `206 Partial Content` означает, что сервер продолжил с нашего места;
  `200` — что сервер начал заново. Во втором случае файл перезаписывается с
  нуля, а не дописывается.
- Ключевая деталь реализации: файл открывается через
  `FileOutputStream(file, resuming)` — **с флагом append**. Обычный
  `file.outputStream()` всегда открывает файл на перезапись и обрезал его, из-за
  чего докачанный файл получался битым. Этот баг уже ловили на живом
  устройстве.
- Размер прогресса при докачке считается как `contentLength + уже скачано`.
- `IOException` всегда считается повторяемой ошибкой: обрыв связи — не
  ошибка, а повод продолжить.

Сверху это складывается в политику WorkManager: экспоненциальная пауза
30 с → 60 с → 120 с, при этом перед повтором ссылка переразбирается заново
(`needsRefresh`).

## 6. Резолверы площадок

Контракт (`domain/resolver/VideoResolver`): по ссылке вернуть `MediaInfo` с
форматами и прямыми ссылками.

### 6.1. YouTube — `data/resolver/youtube/YouTubeResolver`

Используется **NewPipeExtractor 0.26.5** (JitPack). Он сам разбирает страницу,
достаёт itag'и, прямые ссылки и заголовки. Отдельный `NewPipeDownloader`
оборачивает скачивание потока (в него передаётся общий OkHttp-клиент, чтобы
cookie достались и потоку).

Тонкость с качеством, о которой стоит знать (комментарий в коде): без
**PO-токена** YouTube отдаёт только муксированные потоки — видео и звук в одном
файле, — и их выборка обычно ограничена 360p. Потоки `videoOnly` (1080p и
выше) — это DASH без звука: такой файл не воспроизводится, видео и аудио надо
качать отдельно и склеивать. Поэтому в задаче появляется `audioFormat`, который
качается вторым файлом.

NewPipeExtractor требует core library desugaring (использует `java.time`,
`nio`) — это уже включено в `build.gradle.kts`.

### 6.2. TikTok — `data/resolver/TikTokResolver`

Свой парсер на kotlinx-serialization. Сложность в том, что TikTok отдаёт
**две разные схемы разметки**:

1. старая — JSON прямо в странице (api-data);
2. новая — блок
   `<script id="__UNIVERSAL_DATA_FOR_REHYDRATION__">`.

Резолвер сначала пробует новую схему, потом старую. Из найденного объекта
берётся `itemStruct.video.playAddr` — прямая ссылка на файл.

Критично: качать `playAddr` можно **только** с заголовком `Referer` и с
cookie, которые выдал сервер страницы. Поэтому у приложения один общий
OkHttp-клиент с общим хранилищем cookie — файл качается тем же клиентом,
которым парсилась страница.

Мобильный User-Agent (`HttpClientFactory.MOBILE_UA`) — тоже не декорация:
TikTok отдаёт готовые данные именно мобильным запросам, дескортопный упирается
в JS-челлендж.

### 6.3. X (Twitter) — `data/resolver/XResolver`

Используется недокументированный эндпоинт
`https://cdn.syndication.twimg.com/tweet-result?id=<id>&token=<token>`.

Токен считается из id детерминированно (base36 от числового значения id) —
поэтому дополнительных запросов не нужно.

Ответ может быть `mp4` или HLS (`mpegURL` в content-type) — это видно в коде
парсинга.

Слой X самый хрупкий: эндпоинт не документирован и может измениться.

### 6.4. Instagram — `data/resolver/instagram/InstagramResolver`

Публичные посты, Reels и карусели — **без логина и без cookies**.

Цепочка:

1. `mediaId = base64-decode(shortcode)` по алфавиту `A-Za-z0-9-_` —
   чистая функция `InstagramShortcode`, тестируется офлайн;
2. `GET https://www.instagram.com/p/<shortcode>/` с User-Agent
   `Googlebot/2.1` — URL всегда канонический, поэтому `/share/p/` и
   `/reels/` работают так же, как `/p/`;
3. разбор `<script data-sjs>` блоков, в которых встречается
   `"pk":"<mediaId>"`, — JSON разбирается и якорь ищется по `pk`
   (`InstagramCrawler`).

Два решения, которые стоит знать:

- **Якорь по `pk` обязателен.** Страница содержит около 30 чужих `pk`
  (соседние посты того же аккаунта) — «первый `video_versions` в странице»
  вернёт чужой ролик.
- **Ловушка «soft block».** На удалённый, приватный и несуществующий пост
  Instagram отдаёт HTTP 200 и одинаковый SPA-шелл. Поэтому проверяется форма
  тела, а не код ответа, и все три случая дают одну формулировку ошибки.

Форматы: progressive (`video_versions`) и DASH (`video_dash_manifest`).
DASH лучше — 720×1280 @ 2.87 Мбит/с против 480×854 @ 1.47 Мбит/с, — и в нём
есть лестница из шести представлений; выбираем по `width×height`, затем по
`bandwidth`. В ссылке внутри MPD стоит `&amp;` вместо `&`, его обязательно
распаковывать, иначе CDN отдаёт 403.

**Аудио Instagram не отдаёт.** В лицензионных роликах в JSON стоит
`has_audio: false` и `should_mute_audio: true` — площадка вырезает музыку
сама. Поэтому в интерфейсе честно пишется «без звука», а не «со звуком».

### 6.5. SoundCloud — `data/resolver/soundcloud/SoundCloudResolver`

**Прогрессивного MP3 у SoundCloud больше нет**: в августе 2026 весь каталог
переведён на AAC, доступен только HLS. Цепочка:

1. `client_id` — из JS-бандлов `a-v2.sndcdn.com` (`SoundCloudClientId`).
   Ссылка на бандл лежит в тексте страницы, а не в атрибуте `script`, и нужен
   **настольный** User-Agent: с мобильным сайт отдаётся заново (Next.js), где
   бандлов нет. Значение общее у всех, кто скрейпит SoundCloud, поэтому может
   троттлиться — лечится кэшем и переизвлечением при 401/403;
2. `resolve` → метаданные и `media.transcodings[]`;
3. выбор пресета: `aac_160k`, при его отсутствии `aac_96k`; `abr_*` отдаёт
   пустой объект, `snipped` — это превью, не трек;
4. `stream/hls` → подписанная ссылка на m3u8 (подпись живёт ~2 часа).

Сегменты CDN отдаются без единого заголовка — авторизует только подпись в
ссылке.

Загрузка — собственный `domain/engine/HlsDownloader`: разбор m3u8, HEAD-запросы
ради честного процента, склейка `init.mp4` + `.m4s` байтами в валидный fMP4.
Свой загрузчик вместо ffmpeg — потому что ffmpeg у нас только arm64, и
потому что так работает на любом устройстве.

Контейнер по умолчанию — `.m4a` в `Music/TurboFetch`, без перекодирования;
`.mp3` — только по явному выбору юзера (тогда нужен ffmpeg). Промежуточный
файл всегда с расширением исходного потока, иначе вход и выход ffmpeg
совпадают и он падает с «Output same as Input».

### 6.6. Spotify — `data/resolver/spotify/SpotifyResolver`

**Spotify отдаёт только метаданные.** Аудио зашифровано (Widevine DRM):
сырые байты с CDN играют десяток секунд и замолкают, а лицензионные ключи
выдаёт только CDM, недоступный обычному приложению. Публичного API без
секрета тоже нет: `client_credentials` требует `client_secret`, а анонимный
токен из embed-страницы имеет нулевую квоту (429).

Поэтому схема такая: **метаданные из Spotify, звук с YouTube.**

Цепочка:

1. `GET https://open.spotify.com/embed/track/<id>` — страница плеера, в ней
   `<script id="__NEXT_DATA__">` с JSON. Путь данных:
   `props.pageProps.state.data.entity` — название, `artists[]`, `duration`
   (в миллисекундах), обложка в `visualIdentity.image[]`.
   Заголовки не нужны, User-Agent любой, ответ ~10 КБ;
2. если embed не дал данных — обычная страница `/track/<id>`, но только с
   **небраузерным** User-Agent: с обычным Chrome-UA Spotify отдаёт оболочку
   плеера без метаданных, а с `curl/8.5.0` — `<script id="initialState">`
   с base64-JSON;
3. запасной вариант — `oembed`: только название и обложка, без артиста;
4. поиск на YouTube по «артист + название» (`SearchExtractor` + `onFetchPage`);
5. сопоставление кандидатов — `TrackMatcher`.

**Про сопоставление.** Одного названия мало: на YouTube «Song» встречается
сотни раз, а рядом лежат ремиксы, live-версии и «Lyrics». Поэтому:

- названия нормализуются (регистр, пунктуация и служебные слова вроде
  «Official Video» отбрасываются);
- длительность из Spotify — **жёсткий фильтр**: расхождение больше 20 секунд
  отбрасывает кандидата целиком (ремикс — другой трек);
- балл складывается из совпадения названия, артиста и точности длительности,
  бонус дают каналы-дистрибьюторы («Topic», «VEVO»);
- если ни один кандидат не набрал порог, приложение так и говорит: трек не
  найден. Случайный ролик лучше не отдавать.

Найденный трек — это аудиопоток YouTube (`audioStreams`), поэтому для
Spotify действуют те же правила контейнера, что и для SoundCloud: `.m4a` по
умолчанию, `.mp3` по запросу.

## 7. Склейка видео и звука

`data/storage/MediaMuxerMerger` — это `ffmpeg -c copy` на штатных API:

- `MediaExtractor` находит в исходниках дорожку видео и дорожку звука;
- `MediaMuxer` создаёт новый MP4 и принимает `addTrack` для каждой дорожки;
- сэмплы переписываются `writeSampleData` **без перекодирования**.

Буфер сэмпла — 12 МБ с запасом (4K-кадр в худшем случае около 10 МБ).

Почему не ffmpeg: не нужен второй процесс, не нужен NDK-бинарь для базового
сценария, качество не теряется, зависимостей нет.

## 8. Хранилище

Room, версия схемы **3**, `exportSchema = true`, схемы лежат в
`app/schemas/` (1.json, 2.json, 3.json) — по ним видно эволюцию.

Три таблицы:

- `tasks` — очередь. Порядок задаётся колонкой `position` (название `order`
  зарезервировано SQL), запрос `ORDER BY position ASC, createdAt DESC`;
- `settings` — одна строка с настройками;
- `files` — история скачанного: id, taskId, title, fileName, uri, mimeType,
  sizeBytes, source, thumbnailUrl, createdAt.

Миграция `MIGRATION_2_3` создаёт таблицу `files`. Важная деталь: раньше стоял
`fallbackToDestructiveMigration()`, и при смене схемы база пересоздавалась
целиком — очередь загрузок пропадала. Сейчас схема меняется на месте, и
очередь с настройками переживают обновление приложения.

Каждая новая настройка — это новая колонка в `settings` и миграция:
`MIGRATION_3_4` добавила тему и тёмный режим, `MIGRATION_4_5` — флаг
«закрываться после «Поделиться»».

### 8.1. «Закрываться после «Поделиться»`

Настройка отвечает на вопрос «как не открывать приложение, когда делишься
ссылкой». Работает так:

1. `MainActivity` ловит `ACTION_SEND` и **до первой отрисовки** решает,
   закрываться или нет. Настройка читается синхронно (`runBlocking`): чтение
   из локальной SQLite занимает единицы миллисекунд, а решение нужно принять
   до `setContent` — иначе окно приложения мелькнёт;
2. если флаг включён и ссылка опознана (`LinkParser.parse` вернул площадку),
   ссылка уходит в очередь через `QueueViewModel.addLinkDetached`, а activity
   закрывается;
3. `addLinkDetached` работает в **scope уровня приложения**
   (`TurboFetchApp.appScope`), а не в `viewModelScope`: тот отменяется вместе
   с activity, и задача осталась бы в статусе «разбирается» навсегда;
4. если ссылка не опознана — приложение всё-таки открывается, иначе ошибку
   не кому показать.

Системный диалог выбора приложения при «Поделиться» убрать нельзя — это
поведение Android. Убирается именно окно TurboFetch.

Все списки отдаются как `Flow`, UI подписывается — реактивность без ручного
обновления.

## 9. Сеть

Один `OkHttpClient` на всё приложение (`HttpClientFactory.create()`):

- `SimpleCookieJar` — хранилище cookie в памяти;
- таймауты: connect 15 с, read 30 с;
- followRedirects и followSslRedirects включены.

`SimpleCookieJar` хранит cookie **общим списком**, а не «по хосту ответа».
Это важно: cookie с `Domain=.tiktok.com` должна уйти и на `www.tiktok.com`,
и на `v16-webapp-prime.tiktok.com`. Соответствие запросу проверяет сам OkHttp
(`Cookie.matches` — учитывает Domain, Path, Secure). Протухшие cookie
вычищаются по `expiresAt`.

Cookie живут только в памяти и переживать перезапуск приложения не должны.

## 10. UI

Compose + Material3, состояние — `StateFlow`, ViewModel'ы — `androidx.lifecycle`.

**Навигации навигационного стека нет.** `navigation-compose` подключён в
зависимостях, но `NavHost`/`rememberNavController` в коде отсутствуют.
Навигация сделана руками: в `MainActivity` есть `enum class Tab { QUEUE, FILES,
SHRINE }`, состояние вкладки и флага настроек — в `rememberSaveable`, нижняя
панель нарисована вручную (подчёркнутые слова, без Material `TabRow`).
Кнопка «назад» возвращает на предыдущую вкладку, история вкладок хранится
списком **строк** в `rememberSaveable` (enum не переживает сохранение
состояния). Настройки — экран поверх, закрывается через `BackHandler`.

Состояние везде `StateFlow`: `repository.observeAll()` → `Flow` →
`.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial)`,
одноразовые сообщения — `MutableStateFlow<String?>` + `consumeMessage()`, на
экранах — `collectAsStateWithLifecycle()`.

- `ui/queue` — экран очереди: список задач с перетаскиванием за ручку
  (`ReorderState`: у перетаскиваемой карточки отключён `animateItem`, иначе
  она дёргается вторым сдвигом), превью через Coil `AsyncImage` 64×64, статусные
  блоки (прогресс-бар с процентом и «Отменить», «Повторить», «Скачать»),
  плавающая кнопка «Скачать всё»;
- `ui/queue/TaskEditSheet` — `ModalBottomSheet`: чипы качества, чипы качества
  звука (если выбранное видео без звука), тумблер «Только аудио (mp3)», поле
  «Своё имя» и живой предпросмотр итогового имени;
- `ui/files` — история скачанного; удаление убирает **только запись из БД**,
  файл на диске и в галерее остаётся (осознанно, комментарий в коде);
- `ui/settings` — единственный экран на `Scaffold`+`TopAppBar`: чипы качества,
  шаблон имени с живым примером, три переключателя;
- `ui/theme` — «Warm Paper»: палитра `Paper #FAF9F6` / `Ink #16181C` /
  `Rust #9C4A2F`, серифные заголовки, тонкие разделители, прямые углы, без
  карточек. Тёмная палитра объявлена, но не используется;
- `ui/shrine` — «святилище Питера Тиля»: третья вкладка, генератор
  правдоподобных, но никогда не сказанных цитат.

### 10.1. Как устроено «святилище»

Отдельная от загрузчика фича, но разобрать её стоит — там нетривиальная
математика.

`domain/thiel/ThielCorpus` — три списка дословных цитат Питера Тиля:
`STARTUP` (41 фраза из «Zero to One»), `POLITICS` (33 — эссе и интервью),
`ESCHATOLOGY` (34 — пересказ лекций про Антихриста и Катехона).

`domain/thiel/MarkovChain(corpus, order = 2, jumpProbability = 0.18, random)`:

- корпус режется на фразы, слишком короткие (короче `order + 4`) отбрасываются;
- `stream` — все слова корпуса, склеенные **без разделителя** и повторённые 40
  раз: это позволяет переходам перескочить с цитаты на цитату;
- `transitions` — биграммы → следующие слова, `starts` — первые слова фраз;
- `jumpProbability = 0.18` — ключевая деталь: биграмм Тиля почти нет повторов
  (≈8 %), поэтому чистая цепь второго порядка шла бы дословно по исходной цитате.
  С вероятностью 0.18 цепочка перепрыгивает в другое место корпуса, сохраняя
  грамматический стык;
- генерация идёт до границы предложения, максимум 60 попыток; если ни одна не
  дошла до границы — отдаётся целиком настоящая фраза («лучше настоящая цитата,
  чем обрывок»);
- `random` инъецируется — при фиксированном зерне результат воспроизводим.

`ShrineViewModel` работает в двух режимах: **дневной** набор детерминирован
(зерно = `Calendar.DAY_OF_YEAR`, цепь живёт до смены суток) и **свежий**
(кнопка «Открыть ворота», зерно = `System.nanoTime()`). На экране — фото Тиля
(`R.drawable.peter_thiel`, CC BY 2.0, Wikimedia), чипы тем, список цитат с
атрибуцией и явной оговоркой, что цитаты составлены цепью Маркова и Тилю не
принадлежат.

## 11. Тесты

55 юнит-тестов, все проходят без сети (6 пропущены — сетевые спайки).

- `LinkParserTest` (15) — разбор ссылок всех площадок;
- `TrackMatcherTest` (8) — сопоставление трека Spotify с кандидатами YouTube;
- `InstagramShortcodeTest` (3) — shortcode → mediaId (чистая функция);
- `InstagramCrawlerTest` (7) — разбор сохранённой страницы Instagram:
  якорь по `pk`, карусель, DASH-манифест, распаковка `&amp;`;
- `MediaNamingTest` (5) — контейнер, расширение и MIME по набору форматов;
- `MarkovChainTest` (7) — генератор цепи Маркова;
- `FileNameTemplateTest` (5), `QualityPresetTest` (5) — подстановки в шаблон
  имени и подбор формата под пресет качества;
- `SimpleCookieJarTest` (4) — семантика cookie;
- `YouTubeResolverSpikeTest`, `YouTubeDownloadSpikeTest`,
  `InstagramResolverSpikeTest`, `SoundCloudResolverSpikeTest` — спайки по сети,
  включаются явно: `./gradlew :app:testDebugUnitTest -Dturbofetch.network=true`.

Два нюанса, из-за которых в `build.gradle.kts` есть нестандартные настройки:

- `unitTests.isReturnDefaultValues = true` — в юнит-тестах `android.util.Log`
  возвращает заглушку вместо исключения, иначе любой вызов логгера роняет тест;
- для тестов подключён `okhttp-jvm` вместо `okhttp-android`: в okhttp-android
  база суффиксов лежит в assets, а JVM-тесты assets AAR не видят.

Сетевые спайки не падают без сети, а **пропускаются**: внутри стоит
`assumeTrue("Нужен доступ в интернет", ...)`, поэтому без флага тест просто
отмечается как skipped.

Чего в покрытии нет — а это как раз самые рискованные места:

- `DownloadWorker` (весь оркестр, включая решения по составу потоков);
- `RealDownloadEngine` — то есть **докачка и Range не покрыты тестами вообще**,
  хотя именно там уже ловился баг с битым файлом;
- `MediaMuxerMerger` и `MediaStoreWriter`;
- `FfmpegRunner`;
- `TikTokResolver` и `XResolver` (только спайк на YouTube);
- репозитории и все ViewModel'ы;
- `AppContainer` — то есть связность зависимостей тоже не проверяется.

## 13. Узкие места, баги и мёртвый код

### 13.1. Что может выстрелить

1. **Резолверы — главный хрупкий узел.** Разметка TikTok меняется периодически
   (уже было дважды), эндпоинт X недокументирован. Логика парсинга не покрыта
   тестами — регрессии ловятся только на живом устройстве.
2. **mp3 только на arm64-v8a.** На 32-битном устройстве `FfmpegRunner`
   вернёт ошибку с упоминанием `SUPPORTED_ABIS`. Приложение не упадёт, но
   фича не сработает. Архитектуру бинаря заранее никто не проверяет — падает
   уже в момент конвертации.
3. **Подпись NewPipeExtractor — GPL-3.0.** Приложение не публикуется в
   магазинах, поэтому ограничение на распространение не мешает. Если проект
   станет публичным — лицензия станет проблемой.
4. **Состояние загрузки не переживает перезапуск процесса** — оно
   восстанавливается по наличию файла в `cacheDir`, а не по чекпоинтам.
   Очистка кэша системы оборвёт незавершённую загрузку.
5. **Прямые ссылки протухают.** Между probe и фактическим GET может пройти
   минута. Лечится флагом `needsRefresh` и повторным probe, но в худшем случае
   задача будет дёргать разбор несколько раз подряд.
6. **Один клиент на всё приложение** — это плюс для cookie, но и точка отказа:
   cookie-jar в памяти, переживание перезапуска не предусмотрено.
7. **Прямые `Dispatchers.IO` в резолверах** вместо инъекции диспетчера —
   тестировать их без `kotlinx-coroutines-test` неудобно.
8. **Нет instrumented-тестов.** `androidTest` подключён (androidx-junit,
   espresso), но тестов в нём нет: MediaStore, foreground-сервис и W^X-политика
   проверены только на живом устройстве.
9. **Временные файлы живут в `cacheDir` и чистятся только после успешной записи
   в MediaStore.** При неудаче они остаются — это сделано намеренно, чтобы
   докачка продолжила файл с места обрыва. Плата: кэш может пухнуть, а очистка
   кэша системы оборвёт незавершённую загрузку.
10. **Лимит foreground-сервиса `dataSync` (6 ч/сутки).** Комментарий в
    `DownloadWorker` обещает перехват таймаута, но перехватывать нечего:
    `onTimeout()` в WorkManager 2.12 не существует, а `onStopped()` у
    `CoroutineWorker` объявлен `final`. Отмена приходит исключительно как
    `CancellationException`, и раньше её ловили только вокруг скачивания —
    отмена на склейке или записи в MediaStore оставляла задачу в `RUNNING`.

### 13.2. Конкретные баги, найденные при разборе кода

Не «в принципе может», а реальные дефекты с конкретным поведением.

| Симптом | Где | Комментарий |
|---|---|---|
| При обновлении БД версии 1 Room упадёт с «cannot verify data integrity» | `data/db/Migrations.kt` | `version = 3`, а в `Migrations.ALL` только `MIGRATION_2_3`. Пути 1→2 нет, `fallbackToDestructiveMigration` убран |
| Поле «Своё имя» в шторке редактирования молча игнорируется | `worker/DownloadWorker.kt` | `customName` сохраняется в БД, но имя файла строится только из шаблона |
| Скачивание с X приносит текст плейлиста вместо видео | `data/resolver/XResolver.kt` | Варианты с `mpegURL` — это `.m3u8`. Они отдаются как обычные форматы, а `QualityPreset.pick` по `height` (у всех X-форматов `height = 0`) выберет первый отсортированный по битрейту, то есть, скорее всего, именно HLS |
| Докачка может склеить разные потоки | `worker/DownloadWorker.kt` | При `needsRefresh` формат выбирается заново; если поток сменился, частичный файл от старого потока дописывается к новому через `Range` |
| Рассинхрон видео и звука | `data/storage/MediaMuxerMerger.kt` | Сэмплы пишутся сначала все видео, потом весь звук, без чередования по таймкодам. MP4 с неинтерливованными дорожками плохо ищется. Плюс сэмпл больше 12 МБ тихо обрезается: любой отрицательный результат `readSampleData` трактуется как конец файла |
| На Android 8–9 запись упадёт с `SecurityException` | `data/storage/MediaStoreWriter.kt` + манифест | Ветка legacy-пути есть, но `WRITE_EXTERNAL_STORAGE` в манифесте не объявлен. Тот же путь возвращает `file://`-URI, который нельзя передать в intent на N+ (`FileUriExposedException`) |
| В качествах YouTube могут оказаться WebM/AV1 | `data/resolver/youtube/YouTubeResolver.kt` | Фильтр «только mp4» применён к `videoOnly` и `audio`, но не к `muxed` — вопреки комментарию в коде. Их `mimeType` попадёт в MediaStore |
| Cookie TikTok лежит в БД открытым текстом | `data/resolver/TikTokResolver.kt` | `Referer` и `Cookie` кладутся в `MediaFormat.headers` и сохраняются в SQLite как JSON. Плюс: протухший cookie даёт 403 → `retryable = false` → падение без повторного probe |
| Прогресс пишется в БД на каждый 64 КБ | `worker/DownloadWorker.kt` | `updateProgress` = два запроса (get + update) на чанк; для 80 МБ это ~1300 циклов read-modify-write. Плюс гонка: параллельный `updateStatus` может затереть прогресс |
| Бесконечные повторы | `worker/DownloadWorker.kt` | `Result.retry()` без проверки `runAttemptCount` — повторы не ограничены, пауза растёт, но каждый раз делается новый probe |
| Порядок очереди не влияет на порядок скачивания | `worker/DownloadScheduler.kt` | `downloadAll()` ставит задачи отдельными `enqueueUniqueWork`, WorkManager запускает их параллельно (до трёх, лимит — `Semaphore` в воркере). `position` влияет только на отображение |
| Коллизия `position` | `data/db/TaskEntity.kt` | Новые задачи создаются с `order = 0`, а `reorder()` перенумеровывает существующие с 0 — у новой задачи и первой в списке одинаковый `position` |
| Текст ошибки стирается | `data/repo/TaskRepository.kt` | `updateStatus` пишет `errorMessage` (по умолчанию `null`) при любом вызове, включая повтор после «Повторить» |
| `TaskStatus.COMPLETED` недостижим в UI | `worker/DownloadWorker.kt` | После записи воркер удаляет задачу из очереди, поэтому ветка «COMPLETED → Открыть» в `QueueScreen` мертва. Открытие работает только из вкладки «Скачанное» |
| Дедипликация «набора дня» не работает | `ui/shrine/ShrineViewModel.kt` | В цикле `while (quote in ...) { attempt++ }` цитата не генерируется заново — тело цикла пустое |
| `NewPipe.init(...)` — глобальный статик | `data/resolver/youtube/YouTubeResolver.kt` | Инициализация в `init`-блоке: при нескольких экземплярах резолвера (в спайк-тестах он создаётся напрямую) она переинициализируется, в многопоточности это гонка |
| Токен X считается самодельным base36 | `data/resolver/XResolver.kt` | Формула `((id/1e15)*PI).toString(36)` реализована вручную и не совпадает с каноническим JS-форматом. Сервер токен не проверяет, поэтому работает — но сломается непредсказуемо, если проверка появится |

### 13.3. Мёртвый код и незакрытые концы

- `navigation-compose` подключён, но `NavHost` в коде нет: навигация сделана
  руками — вкладки перечислены в `MainActivity` (`enum class Tab`), нижняя
  панель нарисована вручную, история вкладок хранится списком строк в
  `rememberSaveable` (enum не переживает сохранение состояния);
- `FakeEngine` не подключён в контейнере — мёртвый код этапа 1;
- тёмная палитра `PaperDarkColors` объявлена, но помечена `@Suppress("unused")`
  и не используется — тема всегда светлая (`values-night/themes.xml` дублирует
  светлую, чтобы окно не было чёрным);
- `MediaInfo` помечен `@Serializable`, но нигде не сериализуется;
- часть DAO-методов мертва: `TaskDao.count()`, `TaskDao.observe(id)`,
  `FileDao.get(id)`, `FileDao.count()`, `SettingsDao.get`;
- настройки живут в двух местах: `SettingsRepository.observe()` и `current()`
  отдают `AppSettings()` из кода, в БД строка появляется только после первого
  сохранения;
- `sizeLabel` формируется через `String.format` без указания локали — на
  не-русской локали разделителем станет точка.

### 13.4. Что починено в этой же серии (7 ноября 2026)

По итогам разбора сразу исправлено пять вещей — все с проверкой сборкой и
тестами:

- **«Своё имя» теперь работает.** Если поле в шторке редактирования заполнено,
  worker берёт его как имя файла (с санитизацией и добивкой расширения),
  и только при пустом поле откатывается к шаблону настроек;
- **Отмена теперь перехватывается вокруг всего воркера.** Раньше
  `CancellationException` ловили только вокруг скачивания, поэтому отмена на
  склейке или записи в MediaStore оставляла задачу в статусе `RUNNING`
  навсегда. Перехватывать таймаут foreground-сервиса нечем: `onTimeout()` в
  WorkManager 2.12 нет, `onStopped()` у `CoroutineWorker` — `final`;
- **`WRITE_EXTERNAL_STORAGE` добавлен в манифест** с `maxSdkVersion="28"` —
  legacy-ветка записи на Android 8–9 больше не падает с `SecurityException`;
- **HLS-варианты X убраны из списка форматов.** Раньше `.m3u8`-плейлист с
  самым высоким битрейтом попадал в выборку пресета качества, и движок
  скачивал текст плейлиста вместо видео. Теперь при наличии только HLS
  приходит понятная ошибка;
- **Докачка больше не склеивает разные потоки.** Если после повторного разбора
  площадка отдала другой поток, недокачанный файл удаляется и качается заново
  (иначе `Range`-докачка дописала бы байты старого потока к новому).

Остальное из 13.2 — в очереди: миграция 1→2, чередование дорожек в
`MediaMuxerMerger`, фильтр mp4 для muxed-потоков YouTube, ограничение числа
повторов, троттлинг записи прогресса, коллизия `position`, мёртвый цикл
дедупликации в «святилище».
